Introduction

This guide will explain:

  1. The terminology required to learn and use Unicode.
  2. The various actively used Unicode encoding formats.
  3. The methods to encode in, and convert between those formats.
  4. How to manage Unicode data in general.

The guide will not explain coding details and expects you to already have common coding knowledge.

If you'd like to send a suggestion, do so via a github issue on our website's repository.




Terminology

  • Encoding: The method used to store data in computer memory or to transmit it.
  • Code point: A numeric value in a map representing a defined character, command, or segment of a character, which has a specific meaning and task.
    In Unicode, a displayed character consists of at least one code point, but it may consist of multiple, which is why "grapheme clusters" also exist.
    Unicode code points are represented in the format U+N where N is a hexadecimal value from 0 to 0x10FFFF (e.g. the code point for "𒀭" is U+1202D, meaning the code point's value is 0x1202D). Code points under 4 digits are commonly padded with zeroes (e.g. the value of "A" is 0x41, it's written as U+0041).
  • Code unit: A value stored in computer memory representing part of, or a complete code point value. One code unit or a collection of code units might not map directly to a code point value, but rather require a specific algorithm to convert them to the code point's integer value.
  • Grapheme cluster: A sequence of one or more code points that is handled as one displayed unit (e.g. a letter, an emoji 🤯).
  • Planes and blocks: Unicode is divided into 17 planes (the first being plane 0), each plane is divided into blocks, and each block contains a collection of code points for a specific task.
    Most planes are not used and are reserved for future expansion.
    The most notable planes are:
    • The Basic Multilingual Plane (BMP, Plane 0): Ranges from U+0000 to U+FFFF. Contains code points for commonly used languages.
    • The Supplementary Multilingual Plane (SMP, Plane 1), ranges from U+10000 to U+1FFFF. Contains code points for uncommon and historic languages.



Encoding Formats

The commonly used encoding formats are:

  • UTF-8: Uses an 8-bit code unit variable length encoding where each code point consists of 1-4 code units.
  • UTF-16: Uses a 16-bit code unit variable length encoding where each code point consists of 1-2 code units.
  • UTF-32: Uses a 32-bit code unit encoding where each code point is one code unit with the exact same numeric value.

The guide will explain them in detail after the following list.

A few legacy Unicode encoding formats (not important):

  • UTF-7: Uses a 7-bit code unit encoding where each code point value is either a standard 7-bit ASCII character (only if it has the same value as the ASCII character), or a Modified Base-64 number written textually in 7-bit ASCII surrounded by "+" and "-".
    For example, the text "café" would be written as "caf+AOk-". The character "+" can be encoded by writing "+-" or its UTF-7 base-64 value surrounded by "+" and "-".

  • UTF-EBCDIC: A Unicode encoding compatible with IBM's EBCDIC text encoding.
    Uses an 8-bit code unit variable length encoding where each code point consists of 1-5 code units.

  • UCS-2: Uses a 16-bit code unit encoding where each code point consists of a single 16-bit code unit with the exact same value.
    Back then, engineers assumed that 16-bits would be enough for the entirety of Unicode, however, they later realized that their assumption was wrong, and systems were already relying on the 16-bit USC-2 encoding, so the Unicode Consortium reserved a range of code point values to signal the use of a pair of two 16-bit code units, thereby creating UTF-16.

  • UCS-4: Uses a 32-bit code unit encoding where each code point is one code unit with the exact same numeric value.

UTF-32

A UTF-32 code unit contains the exact same value as a Unicode code point in 32 bits. Only 21 bits may be used with the high 11 bits always set to zero, that is for compatibility with UTF-16 pairs which can encode code points only up to the value U+10FFFF, which requires 21 bits as a standard integer (0x10FFFF).

UTF-32 is saved in little-endian or big-endian format, then called UTF-32LE or UTF-32BE. When saving UTF-32 code points into persistent memory (e.g. as a file), or transmitting over a network, or other cases where the recipient cannot reliably assume the endianness,
a Byte Order Mark (BOM) code point is recommended to be inserted at the start of the UTF-16 data to signal the endianness of the text.

The BOM code point is U+FEFF (integer 0x0000FEFF in UTF-32), if saved in a big-endian format its bytes would be {00, 00, FE, FF}, if saved in a little-endian format its bytes would be {FF, FE, 00, 00}, and using these bytes a program can detect the endianness of the text.

There are other methods to detect UTF-32 endianness in dire situations, but they are workarounds and not solutions, the BOM should be used to solve this problem.

UTF-16

A UTF-16 encoded code point consists of either one or two 16-bit code units.

If the code point is in the Basic Multilingual Plane (BMP) (code point ranges from U+0000 to U+FFFF), one code unit is used with the exact same value, however, the values U+D800 to U+DFFF are reserved for the purpose mentioned next.

If the code point is above the BMP (starting from U+10000 and above) it's encoded as a pair of two UTF-16 code units called a surrogate pair, the first code unit being a high surrogate, whose value is in the range U+D800 to U+DBFF, and the second code unit being a low surrogate, whose value is in the range U+DC00 to U+DFFF.
Unpaired UTF-16 surrogates and raw UTF-8 and UTF-32 surrogate code points are invalid Unicode, however, some programs like the Windows operating system allow their use in specific circumstances.

Specific algorithms mentioned later are used to encode and decode UTF-16 code points.

Just like UTF-32, UTF-16 is stored in a little-endian or big-endian format, and is called UTF-16LE or UTF-16BE, and can use a BOM. In UTF-16, the BOM value is the 16-bit integer 0xFEFF, in a big-endian format its bytes are {FE, FF}, in a little-endian format its bytes are {FF, FE}.

UTF-8

A UTF-8 encoded code point consists of one, two, three, or four 8-bit code units.
A UTF-8 code point is esentially a big endian code point integer but with specific bit prefixes at the start of each byte.
A single-code-unit UTF-8 encoded code point shares the exact same values with 8-bit ASCII.

The amount of code units used in one code point is signaled by a specific bit pattern in the leading (first) code unit. Continuation code units contain the bit prefix pattern 102. The prefix patterns allow systems to easily differentiate ASCII from Unicode code point values above ASCII, and to directly convert 8-bit ASCII text data to UTF-8.
In the following table, each four bits in binary (named with the same letter) correspond to one hexadecimal digit in the encoded code point U+uvwxyz:

First code point in range Last code point in range 1st code unit 2nd code unit 3rd code unit 4th code unit
U+0000 U+007F 0yyyzzzz
U+0080 U+07FF 110xxxyy 10yyzzzz
U+0800 U+FFFF 1110wwww 10xxxxyy 10yyzzzz
U+010000 U+10FFFF 11110uvv 10vvwwww 10xxxxyy 10yyzzzz

UTF-8 also has a limit of 21 code point bits.

Specific algorithms mentioned later are used to encode and decode UTF-8 code points.

Examples

The character "Q" is registered as the code point U+0051:

  • In UTF-32, it's encoded as 0x00000051.
  • In UTF-16, it's encoded as 0x0051.
  • In UTF-8, it's encoded as 0x51.

The character "ت" is registered as the code point U+062A:

  • In UTF-32, it's encoded as 0x0000062A.
  • In UTF-16, it's encoded as 0x062A.
  • In UTF-8, it uses two code units, mapping it using the table above, the digits "xyz" in hexadecimal are "62A",
    the conversions to binary are x = 0x6 = 1102,   y = 0x2 = 00102,   z = 0xA = 10102. Mapping it to binary as {110-xxx-yy, 10-yy-zzzz}, the UTF-8 code units are {110-110-00, 10-10-1010} (in hexadecimal {0xD8, 0xAA} *0xD8 is a coincidental result not to be confused with the high surrogate code point U+D800*).

The character "𒀶" is registered as U+12036:

  • In UTF-32, it's encoded as 0x00012036.
  • In UTF-16, it's encoded as a surrogate pair {0xD808, 0xDC36}.
    The UTF-16 surrogate pair encoding algorithm is explained later in this document.
  • In UTF-8, it uses four code units, encoded as {0xF0, 0x92, 0x80, 0xB6}.



Conversion between Encoding Formats

In this document, saying "converting UTF-32" to UTF-16 or UTF-8 has the the same meaning as saying "encoding a code point" in those two encodings, as UTF-32 uses 32-bit integers with the exact same value as code points.
To encode a code point in UTF-32, you simply set a 32-bit integer to the code point's value. The document will explain (using the C programming language) how to convert:

  • UTF-32 to UTF-16 and UTF-8.
  • UTF-16 to UTF-32 and UTF-8.
  • UTF-8 to UTF-32 and UTF-16.

The code blocks below contain C functions that convert one code point only and with limited input validation in native platform endianness, the reader should implement their own algorithms that suit their goals.

UTF-32 to UTF-16

If the code point is in the BMP (from U+0000 up to U+FFFF), it's simply encoded as a 16-bit integer with the same value. If the code point is outside the BMP (U+10000 and above), the following must be done to encode it as a UTF-16 surrogate pair:

  • Subtract 0x10000 from the code point value, resulting in a minimum value of 0 and a maximum of 0xFFFFF, which fits in 20 bits. The 20 bits are divided into two 10-bit segments.
  • The high segment gets prefixed by 1101102 (or gets added to 0xD800), creating the 16-bit high surrogate in the range 0xD800 to 0xDBFF. The high surrogate is the first code unit.
  • The the low segment gets prefixed by 1101112 (or gets added to 0xDC00), creating the 16-bit low surrogate in the range 0xDC00 to 0xDFFF. The low surrogate is the second code unit.

UTF-16 to UTF-32

Decoding UTF-16 code points (or converting them to UTF-32) is the opposite of encoding: If the code point is in the BMP (one UTF-16 code unit), it's simply expanded to 32-bits. If the code point is encoded as a surrogate pair outside the BMP:

  • Extract the high 10-bit segment off the high surrogate (or subtract 0xD800 from it)
  • Extract the low 10-bit segment off the low surrogate (or subtract 0xDC00 from it)
  • Combine the two segments into one 20-bit integer.
  • Add 0x10000 to get a 32-bit integer (UTF-32)

UTF-32 to UTF-8

The structure of a UTF-8 encoded code point is similar to the bytes of a big-endian integer containing the code point value, however, UTF-8 is a variable length encoding, and its code units contain specific bit prefixes to signal their position in the code point.

  • If the code point is in the range U+0000 to U+007F: It's simply encoded directly as an 8-bit integer with the exact same value of the code point (maps directly to 8-bit ASCII).
  • If the code point is in the range U+0080 to U+07FF: It's encoded as two code units, the leading (first) code unit starts with the prefix 1102 to signal the use of two code units for the current code point.
  • If the code point is in the range U+0800 to U+FFFF: It's encoded as three code units, the leading (first) code unit starts with the prefix 11102 to signal the use of three code units for the current code point.
  • If the code point is in the range U+010000 to U+10FFFF: It's encoded as four code units, the leading (first) code unit starts with the prefix 111102 to signal the use of four code units for the current code point.
  • Continuation code units start with the prefix 102 to signal that the current code unit isn't a leading code unit.
  • The actual data bits aside from the prefix patterns are defined in the following table where each four bits in binary (named with the same letter) correspond to one hexadecimal digit in the encoded code point U+uvwxyz:
First code point in range Last code point in range 1st code unit 2nd code unit 3rd code unit 4th code unit
U+0000 U+007F 0yyyzzzz
U+0080 U+07FF 110xxxyy 10yyzzzz
U+0800 U+FFFF 1110wwww 10xxxxyy 10yyzzzz
U+010000 U+10FFFF 11110uvv 10vvwwww 10xxxxyy 10yyzzzz

UTF-8 to UTF-32

Decoding UTF-8 code points (or converting them to UTF-32) is the opposite of encoding: The length of the UTF-8 code point is determined by the bit prefix pattern, then the code point bits in each code unit are extracted into the resulting 32-bit integer (UTF-32).
